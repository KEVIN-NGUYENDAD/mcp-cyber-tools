**The single most informative fact: both runs returned the same version.**

Run 1 and Run 2 are ~3 hours apart, yet both read content matching `9d1e6e3`
(`21:55:53Z` / `unknown: 4`). This is not drifting staleness — it is a fixed
version being returned repeatedly. A cache that merely lags would have rolled
forward to `22391bc` between the two runs.

**Direction of error.** Both occurrences were harmless: they reported a coverage
gap that had already been closed. The same defect pointed the other way —
reporting GREEN over a control disabled after the cached snapshot was taken —
would be a monitoring system actively concealing an incident.

## 3. Possible causes, and evidence against each

### A · GitHub CDN cache (`raw.githubusercontent.com`)

*Hypothesis:* the ~5-minute edge cache served an old object.

**Evidence against — strong.** At Run 2 verification, a direct fetch of the same
URL with `Cache-Control: no-cache` returned `22:10:01Z` (`ETag
651d7d96…`, `x-served-by cache-phx1710143-PHX`). The stale read persisted
2 h 51 m — roughly 34× the documented TTL. The API, which does not share that
cache, agreed with the CDN.

**Verdict: effectively ruled out** as the sole cause. Cannot explain a 3-hour
persistence, and cannot explain the same version being returned twice.

---

### B · Cache in the scheduled task's fetch layer

*Hypothesis:* the platform's fetch caches by URL, independently of CDN headers.

**Evidence for:** persistence far beyond CDN TTL; local fetches from the same
machine to the same URL were unaffected, so the divergence is client-side.

**Evidence against:** none observed.

**Untested:** no visibility into request or response headers as seen by the task.

**Verdict: plausible.** Consistent with everything observed, but not
distinguishable from C without a controlled test.

---

### C · Snapshot pinned at the task's first successful fetch

*Hypothesis:* content fetched on the task's first successful run is retained and
replayed on subsequent runs.

**Evidence for — strongest fit.** The stale content is *exactly* the version
that was current when the task first ran successfully (`9d1e6e3`, published
21:56:18Z). Two runs ~3 hours apart returned that same version rather than
progressively newer ones. A time-based cache should have expired and rolled
forward; a pinned snapshot would not.

**Evidence against:** none, but the hypothesis rests on a single version being
observed twice — a small sample.

**Verdict: best-fitting hypothesis, low confidence.** Needs the test in §6.

---

### D · Wrong ref, path, or mirror

*Hypothesis:* the task resolved a different branch, path, or host.

**Evidence against:** the content returned is a real, previously-published
version of the correct file from the correct branch, not a different file and
not an error.

**Verdict: ruled out.**

## 5. Missing data

Listed in the order that would most reduce uncertainty.

**1 · Whether the mitigation was actually applied.**
A cache-busting parameter and an age check were drafted for the scheduled task
prompt. It has not been confirmed that the prompt was updated. If it was not,
then no mitigation is in effect and MONITOR is measuring nothing.

**2 · A bulletin run since `a0a6722` (07:19:38Z, 2026-08-31).**
A third distinct published version now exists. The next real scheduled run is a
natural experiment:

| Result | Interpretation |
|---|---|
| Returns `07:19:09Z` | Mitigation working, or defect not currently present |
| Returns `22:10:01Z` | Time-based cache — hypothesis B |
| Returns `21:55:53Z` again | **Pinned snapshot — hypothesis C confirmed** |

The third outcome would be decisive: returning the *oldest* of three available
versions cannot be explained by any time-based expiry.

**3 · The bulletin's own generation timestamp.**
Neither observed bulletin stated when it ran. Lag can only be bounded, not
measured. The mitigation's age check should surface this.

**4 · Whether the 20:10 bulletin fired on 2026-08-30 at all.**
The 19:45 chain ran late (00:18:52 on 08-31, via `-StartWhenAvailable`),
suggesting the machine was unavailable that evening. If the bulletin did not
fire, Day 1 of the observation period has no bulletin observation either way.

**5 · Response headers seen by the task's fetch layer.**
`Age`, `ETag`, and `x-served-by` from inside the task would separate B from C
immediately. Not currently obtainable.
